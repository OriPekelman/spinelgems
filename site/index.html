The Spinel compatibility catalog

Spinel is an ahead-of-time Ruby compiler that accepts a deliberately-growing subset of Ruby. Its package manager is spin — a spin.toml manifest resolved against the serverless spin-index. SpinelGems is the compatibility oracle underneath: a wholesale survey of the ~189k gems on rubygems.org, re-classified at each engine revision by whether they actually compile under the subset — i.e. which ones could become spin packages.

Gems and spin packages are separate worlds by design — no gemspec, no runtime require, no tarballs; sources splice into one whole-program AOT compile. They meet only at the name: a rubygems name reused in spin means “the same library, possibly a subset-compatible port.” SpinelGems measures which gems sit on the right side of that line — and is the intended seed for spin-index.

How it feeds spin

  1. Candidate ports. The clean / loaded / verified tiers are the pool a spin-package port can start from — the gems whose source already compiles under the subset today.
  2. Compatibility as metadata. Every verdict is keyed on the exact engine revision (the compiler’s git SHA) — the same shape as spin-index’s probe records, which note which compiler build a release passed or failed its tests under. Bump the engine → re-probe → a gem rejected today clears the moment the feature it needs lands.
  3. Index seed. The ~189k-gem probe corpus is the intended seed for spin-index’s name → (repo, releases) map, and the running measurement of the subset’s reach.

The verdict ladder

★ verifiedfull surface compiles and a behaviour smoke matches CRuby under a Spinel-compiled harness — the only verdict to trust where it matters
○ loadedcompiles and loads identically (require-only) — logic untested
✓ cleancompiles clean (cheap lower bound); no behaviour run
~ riskycompiles, but uses constructs Spinel degrades silently (define_method, eval, send…)
✗ rejecteddoesn't compile, or a caught miscompile — each reason names the missing feature

How the catalog is built

  1. Compile + scan (a lower bound). Each gem’s lib/ entrypoints are compiled as a Spinel program and the diagnostics classified → clean / risky / rejected. This only means “the C came out,” not “it works.”
  2. Differential CRuby parity (the trustworthy check). For the ones that compile, a per-gem behaviour smoke runs once under CRuby and once Spinel-compiled, and the outputs are diffed. Match → verified; mismatch → a caught miscompile, filed upstream. CRuby-as-oracle is exactly spin’s own verification methodology (spin test).

Using spin

spin new mylib --lib          # scaffold a package (spin.toml, tests)
spin add ansi --git https://github.com/you/spinel-ansi
spin test                     # run against CRuby as a parity oracle
spin publish                  # PR a release into spin-index (tests gate)

The full guide is docs/spin.md; the design record is internals/spin.md.

The probe is a lower bound — Spinel’s whole-program model means multi-file gems under-probe, and silent miscompiles are invisible to a compile-only pass. Trust verified, not clean, where it matters.
