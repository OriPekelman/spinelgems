Dependencies for Spinel projects

Spinel-compiled projects have no shared way to declare or exchange dependencies, so each vendors by hand. Rather than design a package manager, borrow a format everyone already knows — a standard Gemfile — and revisit later.

The convention

source "https://rubygems.org"
ruby "3.3.0", engine: "spinel", engine_version: "0.0.0"

gem "tep", git: "https://…/tep.git"   # siblings via path:/git: (replaces rsync)
gem "some_pure_ruby_lib"

bundle lock resolves normally (it ignores the engine marker); the marker guards bundle install. Nothing here is novel — that's the point.

The plugin does two things

  1. Makes it work. Spinel has no load path and inlines require_relative, so a dependency has to be placed where Spinel will follow it. spinel-compat vendor does that from a lockfile.
  2. Gates. Spinel silently emits a no-op for unsupported Ruby (exit 0), so “it compiled” ≠ “it works”. The plugin probes gems and flags incompatible ones at bundle lock time, with reasons that name the missing feature.

The verdict ladder

★ verifiedcompiles clean and the gem's own tests pass through a Spinel-compiled harness — the only verdict to trust where it matters
✓ cleancompiles clean, no risky constructs found cheaply
~ riskycompiles, but uses constructs Spinel degrades silently (define_method, eval, send…)
✗ rejectedan unsupported call, or analyze failed — the gate fails the lock

Quick start

# make it work — place deps where Spinel finds them
bundle lock
spinel-compat vendor                 # -> vendor/spinel/<gem>/lib + deps.rb

# gate — flag what Spinel can't compile, early
spinel-compat check Gemfile.lock     # exit 1 if any gem is rejected

The probe is a lower bound — Spinel's lack of a load path means multi-file plain-require gems under-probe, and silent miscompiles are invisible to it. Trust verified, not clean, where it matters.
